Obfuscation

发表于2026-11-08|更新于2026-11-08|笔记
|浏览量:

这里是吧之前乱糟糟的笔记结合一些题目跟大肥鱼聊了一下的返回，我觉得很精辟，整个端上来让大家品鉴一下~

理解核心概念——到底什么是“代码混淆”？
我们先从最根本的问题开始。

  1. 代码混淆是什么？
    文章里给出了一个很清晰的定义：
    代码混淆是一种代码转换技术，它把原本清晰、易读的代码，转换成功能上完全一样，但结构和逻辑上极其复杂、难以理解的代码。
    简单来说，就是“把简单的事情搞复杂”，让想破解你的人看不太懂。
  2. 为什么要做代码混淆？
    文章提到，它的根本目的就是干扰逆向工程，保护知识产权。在CTF比赛里，它也是常见的题目类型。
  3. 混淆发生在哪个层面？
    文章将混淆分成了两大类：
    • 源码级混淆：在源代码（如C、Java代码）层面动手脚。
    • 机器码混淆：在编译后的二进制机器码层面动手脚。
  4. 常见的混淆手段有哪些？
    文章列举了一些典型例子：
    • 标识符重命名：把有意义的变量名（如 password）改成无意义的（如 a1b2c3）。
    • 等价表达式替换：把简单的 a = a + 1 换成复杂的等价形式。
    • 花指令：插入一些垃圾数据，干扰反汇编器，让它解析出错。
    • 平坦控制流：把程序的正常逻辑（if/else、循环）全部打散，重组为统一的 switch 结构，让控制流图看起来像一张“大饼”。
    • 指令替换：用多条功能复杂的指令，替换一条简单的指令。
    第二步：花指令混淆的核心原理
    我们花几分钟把花指令讲透，这是你后续理解更复杂混淆的基石。
  5. 花指令到底长什么样？
    文章里用一句话概括了花指令的本质：
    花指令是故意插入到代码中的垃圾数据/垃圾指令，其目的是干扰反汇编器，让静态分析工具（如IDA、Ghidra）把数据误判为代码，或者把代码误判为数据，从而呈现错误的逻辑。
    重点：它干扰的是反汇编器，而不是CPU。CPU执行时，会通过jmp（跳转）指令直接跳过这些垃圾数据，所以程序运行结果完全正常。
  6. 为什么反汇编器会上当？——两种反汇编算法的较量
    文章提到了关键点：反汇编算法主要有两种：
    • 线性扫描（Linear Sweep）：从头到尾，逐字节挨个解析，不管当前是否是跳转目标。这种算法最容易被花指令欺骗。
    • 递归遍历（Recursive Traversal）：顺着程序的执行流（call、jmp）去分析，只解析能到达的地址。这种算法相对聪明，但遇到复杂的控制流时仍会出错。
  7. 经典的花指令实例（你得看明白这个）
    这是文章里提到的最基础、最经典的x86花指令模式：
    asm
    jmp label1 ; 无条件跳转到 label1
    db 0xE8 ; 插入一个字节的垃圾数据（0xE8 恰巧是 CALL 指令的机器码开头）
    label1:
    … 正常代码 …
    我们来模拟一下CPU和反汇编器的视角：
    • CPU执行时：遇到 jmp label1，直接跳走，完全无视下面那个单独的 0xE8 字节。程序稳稳地运行。
    • 反汇编器（线性扫描）：不管跳转，按顺序来。它解析完 jmp label1 后，把下一个字节 0xE8 当成一条指令的开头。0xE8 是 CALL 指令，它后面需要跟4字节的地址。于是反汇编器会把这1个垃圾字节 + 后面的4个字节（可能是正常代码）强行拼成一条 CALL 指令。结果导致后面所有的代码解析全部错位（反汇编乱套了），你看到的逻辑就全乱了。
    第三步：控制流平坦化的核心原理
    如果说花指令是给反汇编器“下绊子”，那么平坦化就是给分析者的大脑“上难度”。它把程序原本清晰的逻辑结构彻底打散。
  8. 它把代码变成了什么样子？
    文章里提到，平坦化会把所有基本块（代码片段）的“先后顺序”打乱，然后统一交给一个 “分发器（Dispatcher）” 来管理。
    我画一个简化版的对比图给你看：
    • 正常代码（伪代码）：逻辑清晰，像流水线。
    text
    开始 -> [判断条件A] –真–> [执行X] –> 结束
    –假–> [执行Y] –> 结束

• 平坦化之后（伪代码）：变成了“旋转门 + 门票”的模型。
text
初始化“门票”变量 = 起始块编号

┌─> [分发器] –根据“门票”编号，决定跳转到哪个块
│ |
│ ├—> [块1：执行操作，然后设置下一张门票 = 块3的编号] —-┐
│ ├—> [块2：执行操作，然后设置下一张门票 = 块4的编号] —-┘
│ └—> [块3：判断条件，真则设置门票=块1，假则设置门票=块2]
│ |
└──────────────────（循环跳回顶部的分发器）<—————-──┘
2. 它为什么让逆向变得困难？
• 原本的 if/else 判断逻辑，被拆散到了不同的代码块里。
• 你顺着IDA的流程图看，会发现所有代码块最终都指回同一个分发器，流程图看起来像一张庞大的蜘蛛网或意大利面，你很难一眼看出哪个块先执行、哪个块后执行。
• 只有动态调试（一步步跟寄存器和状态变量），才能追踪到真实的执行路径。
3. 一个极简的伪代码感受一下
假设原始逻辑是：
c
if (a > 10) {
result = 1;
} else {
result = 0;
}
平坦化后，逻辑变成了类似这样（极度简化版）：
c
int state = 0; // 门票
while (state != 999) { // 循环分发器
switch(state) {
case 0: // 入口
if (a > 10) state = 1; else state = 2;
break;
case 1: // 真分支
result = 1;
state = 999; // 结束
break;
case 2: // 假分支
result = 0;
state = 999; // 结束
break;
}
}
你看，原本的 if/else 结构消失了，变成了一个巨大的 switch 轮询。
第四步：手撕平坦化的实战方法论（定位 + 恢复）
当你拿到一个被OLLVM平坦化混淆的程序，两眼一抹黑时，记住这套标准破局三板斧，比硬看代码重要一万倍。

  1. 第一板斧：定位“分发器”和“状态变量”
    • 找分发器：在IDA或Ghidra里，顺着函数入口进去，通常第一眼看到的就是一个巨大的 while (1) 或 do…while 循环体，里面套着一个巨大的 switch 语句。这个巨大的 switch 就是分发器。
    • 找状态变量：在分发器跳转之前，一定会有一个变量被反复赋值并用于 switch 判断。这个变量通常是局部变量（如 v1、v5），它就是状态变量（门票）。记住它的名字（比如 v1）。

  2. 第二板斧：动态调试追踪（最直观的方法）
    • 既然静态看乱，咱就用动态调试（如x64dbg、IDA远程调试）。
    • 在分发器的 switch 跳转表处下断点，单步执行。
    • 每一次经过分发器，紧盯状态变量（v1）的变化。你会看到类似这样的轨迹：
    o 入口处：v1 = 0 -> 执行Block_A，结束后 v1 = 5
    o 回到分发器：v1 = 5 -> 执行Block_B，结束后 v1 = 10
    o 回到分发器：v1 = 10 -> 执行Block_C，结束后 v1 = 999（退出）
    • 把这串执行序列记下来（比如 0 -> 5 -> 10 -> 999），你就找到了真实的执行流。

  3. 第三板斧：静态恢复逻辑（结合记录）
    • 回到IDA的静态代码窗口，搜索状态变量 v1 == 5 的分支，查看该分支里的核心操作（加减乘除、比较、函数调用）。
    • 把你用动态调试记录的序列，对应到静态代码的操作上。
    • 比如你记录到 v1=5 时做了加法，v1=10 时做了比较。把这两段代码拼起来，原始的 if-else 逻辑就浮出水面了。
    第五步：实战演练 —— 手撕一个平坦化示例
    假设有一段被混淆的伪代码（这正是你博客里会出现的典型结构）：
    c
    // 这是一个被平坦化后的函数，逻辑被拆散了
    int confused_func(int a) {
    int state = 0; // 这就是我们要盯住的“门票”
    int result = 0;

    while (1) { // 巨大的分发器循环
    switch (state) {
    case 0: // 入口块
    if (a > 10) {
    state = 2;
    } else {
    state = 3;
    }
    break;

    case 2: // 真分支块
    result = 100;
    state = 999;
    break;

    case 3: // 假分支块
    result = -1;
    state = 999;
    break;

    case 999: // 退出块
    return result;
    }
    }

}

现在我们按照你总结的方法，一步步“手撕”它：
第一步：定位门票和分发器
• 我们看到巨大的 while (1) + switch(state)，这就是分发器。
• 变量 state 就是我们要盯的门票。
第二步：动态追踪门票轨迹（这里我们在脑子里模拟运行）
• 假设传入的 a = 5：
o 入口 state = 0，因为 5 > 10 为假，所以 state 被赋值为 3。
o 再次循环，state = 3，执行 case 3，result = -1，然后 state = 999。
o 再次循环，state = 999，直接 return -1。
o 门票轨迹：0 → 3 → 999
• 假设传入的 a = 20：
o 入口 state = 0，因为 20 > 10 为真，所以 state 被赋值为 2。
o 再次循环，state = 2，执行 case 2，result = 100，然后 state = 999。
o 再次循环，state = 999，直接 return 100。
o 门票轨迹：0 → 2 → 999
第三步：反向查分支，把逻辑“拼起来”
• 查 state = 0 时：发现它是在做 条件判断（比较 a > 10），并且把结果映射到了门票 2（真）和门票 3（假）。
• 查 state = 2 时：发现它是 真分支的操作（result = 100）。
• 查 state = 3 时：发现它是 假分支的操作（result = -1）。
• 查 state = 999 时：发现它是 返回结果。
第四步：恢复原始逻辑
把这三段拼回正常的 if-else 结构：
c
int original_func(int a) {
int result;
if (a > 10) {
result = 100;
} else {
result = -1;
}
return result;
}
看，原本像意大利面一样的代码，经过你刚才的“拆门票”分析法，瞬间还原成了清晰的两三行逻辑！
第六步：字符串加密的核心原理

  1. 它解决了什么问题？
    正常情况下，你用IDA打开一个程序，在“Strings”窗口可以直接看到所有明文，比如：
    • “C:\Windows\System32"
    • “Password is correct”
    • “http://api.example.com/login“
    逆向者一看就知道程序要访问哪个网站、调用哪个系统路径。字符串加密的目的，就是让这些敏感信息在二进制文件里“消失”，运行时再变回明文。
  2. 它最经典的实现方式是什么？
    绝大多数字符串加密都遵循这个通用模式：存储密文 → 运行时解密 → 用完即焚（可选）。
    最最最常见的算法就是 XOR（异或）逐字节解密。伪代码类似这样：
    c
    // 原来要用的字符串明文是 “admin”
    // 编译前先把它加密（例如每个字节异或 0xAA）：
    // ‘a’(0x61) ^ 0xAA = 0xCB
    // ‘d’(0x64) ^ 0xAA = 0xCE
    // ‘m’(0x6D) ^ 0xAA = 0xC7
    // ‘i’(0x69) ^ 0xAA = 0xC3
    // ‘n’(0x6E) ^ 0xAA = 0xC4
    // 程序里只存储这一串乱码字节： CB CE C7 C3 C4

// 运行时，执行一个解密函数：
char encrypted[] = {0xCB, 0xCE, 0xC7, 0xC3, 0xC4, 0x00};
char key = 0xAA;
for (int i = 0; i < 5; i++) {
encrypted[i] = encrypted[i] ^ key; // 异或后变回 “admin”
}
// 此时 encrypted 就是明文 “admin”，可以拿去 strcmp 了
3. 它为什么增加分析难度？
• 你在静态反汇编里搜 “admin”、”password” 这些关键词，搜不到。
• 代码中会出现一段无意义的循环（for 或 while），里面做异或、加减等运算。如果不动态调试，仅凭肉眼很难看出这段循环解密完的结果是什么。
第七步：两招定位字符串解密点
第一招：顺藤摸瓜（看交叉引用）
如果你在IDA里发现了那堆乱码（密文）的地址（比如 .data 段里一串无意义的字节），直接查看它的交叉引用（Cross-reference，按 X 键）。哪个函数引用了这堆乱码，哪个函数就是解密函数。进入该函数后，找循环结构（for 或 while），循环的结束花括号（}）后面，就是你应该下断点的位置。

第二招：守株待兔（API断点回溯）—— 这招最无敌！
请记住一个永恒的逻辑：加密藏得再深，最终的目的都是为了“用”。

如果这个字符串是拿来对比密码的，它最终一定会传给 strcmp、memcmp 或 wcscmp。

如果这个字符串是拿来弹出提示框的，它最终一定会传给 MessageBoxA。

如果这个字符串是拿来打开文件的，它最终一定会传给 CreateFileA。

实战操作如下：
你直接在调试器里给目标 API 函数（比如 strcmp）下断点。程序运行触发这个 API 时，会立刻断下来。此时，你查看调用堆栈（Call Stack），返回到上一层调用者的地址。那个返回地址处的代码，就是解密循环结束后的位置。这时候，你查看 strcmp 的两个参数寄存器（如 EAX、EDX 或 RCX、RDX），明文字符串就已经赤裸裸地躺在内存里了。你甚至不需要去分析它用了异或还是 AES，直接就能截获结果。
第八步：指令替换的核心原理

  1. 它到底是什么？
    它的核心思想是：用一组功能等价但更复杂/更长的指令，替换掉原来那条简单指令。
    • 原来：eax = eax + 1 （一条指令）
    • 替换后：eax = eax + 5; eax = eax - 4; （两条指令，结果还是 +1）
    • 再夸张点：eax = eax ^ 0xAA; eax = eax ^ 0xBB; （利用两次异或互相抵消，0xAA ^ 0xBB 的净效果等同于加某个常数）
  2. 常见的手法有哪些？
    文章里提到了几种典型“废话文学”：
    • 算术替换：把 a = a + 1 变成 a = a + 10; a = a - 9。
    • 位运算替换：把 a = a * 2 变成 a = a << 1（左移，这个还好）；或者更绕的 a = (a ^ a) + (a + a)（纯粹恶心人）。
    • 插入无关指令：在关键指令前后插入大量不改变任何寄存器的 nop（空操作）或 mov eax, eax（自赋值）。
  3. 它为什么让逆向变难？
    • 代码膨胀：原本 10 行的逻辑，可能变成 100 行甚至 1000 行汇编，阅读量暴增。
    • 干扰常量识别：你想要找的常数（比如密钥 0x5A）被拆散成 0x10 + 0x20 - 0x? 等运算，你不算一遍根本不知道最终值是多少。
    • 扰乱模式匹配：杀毒软件或自动分析工具靠特征码识别程序，把指令打碎后，原来的特征字节序列就失效了。
    虚假控制流（Opaque Predicates）
    现在我们来到你博客里提到的最后一种常见混淆：虚假控制流。
  4. 它长什么样？
    它在代码里插入大量 “永远为真” 或 “永远为假” 的条件判断（if 语句）。
    比如：
    c
    // 原始逻辑很简单：a = a + 1;

// 混淆后：
int x = 10;
int y = 20;
if (x * y == 200) { // 1020 永远等于 200，所以这个 if 永远为真
a = a + 1; // 真正的逻辑在这里
} else {
// 这一坨代码永远也不会被执行（死代码 Dead Code）
a = a * 100;
a = a / 3;
// … 几百行垃圾运算
}
2. 它为什么恶心人？
• 它把 IDA 的流程图（控制流图）撑得巨大无比，到处都是分叉。
• 它会插入大量永远走不到的垃圾代码，浪费你逐行阅读的时间。
• 如果多层嵌套，分析者很容易眼花缭乱，把真正逻辑搞丢。
3. 你的“秒杀”破法（核心！）
面对这种混淆，千万不要去分析那个条件（比如 xy==200）到底成不成立！ 记住这两招：
• 第一招（静态 - 最推荐）：直接按 F5 看反编译伪代码。IDA 和 Ghidra 的常量传播优化（Constant Propagation）会自动识别出这种永真/永假的条件，直接把死代码（else 分支）灰掉或者删掉，你看到的伪代码里，往往只剩下真正的 a = a + 1。
• 第二招（动态 - 绝对真理）：开调试器，单步跟踪。当你遇到 if (x*y == 200) 时，你会发现程序永远只会走进 True（真）分支，那个 False（假）分支的代码，你永远不用看，程序永远不会执行它。
总结一句心法： “假的永远走不到，真的只有一小条。” 动态跟一遍，或者 F5 看化简，垃圾代码瞬间灰飞烟灭。
