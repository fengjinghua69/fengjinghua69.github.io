PE-import

发表于2026-11-20|更新于2026-11-23|笔记
|浏览量:

在学习导入表之前，我们要搞清楚这样几个问题。

  1. 调用DLL的原理

    调用DLL函数主要有两种方式：

    1. 隐式调用（使用导入表，最常见）编译链接阶段：
      代码中直接调用函数（如 MessageBoxA），并链接对应的导入库（.lib）。
      链接器根据 .lib 的信息，在PE文件中生成导入表，记录需要的DLL名和函数名（或序号）。
      代码生成间接调用指令：call dword ptr [IAT中的地址]。
      此时PE文件里存的是函数名，不是真实地址。
      运行时：
      Windows加载器读取导入表，自动加载对应的DLL，解析出函数真实地址，并写入IAT。
      程序通过IAT间接调用真正的函数。
      注意：加载和解析地址是加载器内部完成的，并不是调用你代码里的 LoadLibrary / GetProcAddress。
    2. 显式调用CHMODULE h = LoadLibraryA(“user32.dll”);
      auto pFunc = GetProcAddress(h, “MessageBoxA”);
      pFunc(…);
      不会生成导入表项。
      函数名以普通字符串形式存在。
      完全由程序员手动控制加载和获取地址。

  2. 一个进程空间中的EXE和DLL是如何被加载到内存的？

    每个32位进程拥有独立的4GB虚拟地址空间（高2G内核，低2G用户）。
    加载器先把EXE映射到内存（按SectionAlignment对齐，通常是0x1000页对齐）。
    解析EXE的导入表，依次加载它依赖的所有DLL（也会解析DLL自己的导入表，形成依赖树）。
    每个模块都有自己的基址（ImageBase，实际加载可能因ASLR而变化）。
    加载完成后，EXE和所有DLL都映射在同一进程的用户地址空间里，彼此可见。

  3. EXE调用的动态链接库在内存中与在硬盘中有什么不同？

    硬盘（PE文件）状态：IAT位置存放的是函数名相关的信息（指向IMAGE_IMPORT_BY_NAME的RVA，或序号）。此时还没有真实地址。(隐式调用)
    内存（已加载）状态：加载器已经把IAT里对应位置改写成了真实函数地址（VA）。

精细流程

调用分为显式调用和隐式调用。
首先dll源码被编译器编译为DLL.obj之后链接器用DLL.obj输出DLL.dll和dll.lib
其中DLL.dll是DLL文件，里面有代码，也有导出表，其中记录着它提供的函数和地址的偏移。而lib是导入库，他里面没有函数的机器码，只记录哪些函数来自哪个DLL文件。

隐式调用：使用.lib。写main.c，里面直接调用函数，编译器把.c文件编译成obj文件，里面的函数是未解析符号，把.lib和.c给链接器，链接器读.lib知道函数来自.dll，链接器依此创造导入表，在EXE的IAT里存的是指向函数名的RVA(里面存放的是函数的名字)，之后加载器把EXE加载到内存中，读EXE的导入表，知道它需要什么函数，加载器就加载.dll到内存中，之后加载器读.dll的导出表找到函数的RVA，之后计算VA，写进EXE的IAT中，覆盖之前的RVA

显式调用：写main.c，使用LoadLibraryA(“DLL.dll”)和GetProcAddress(h,”Add”)
不使用.lib，里面没有函数的未解析符号，只有LoadLibraryA、GetProcAddress 的调用，链接器使用main.obj和kerne132.lib，而在EXE的导入表里面只有kernel32.dll 的 LoadLibraryA 和 GetProcAddres。而加载器启动exe的时候，加载器只处理kernel32.dll，代码执行 LoadLibraryA(“MyDll.dll”)，这时才加载 DLL 到内存，代码执行 GetProcAddress(h, “Add”)，这时才读 DLL 的导出表，按名字找 RVA，加基地址，返回真实地址。

DLL 侧：
MyDll.h + MyDll.cpp -> 编译 -> MyDll.obj -> 链接 -> MyDll.dll + MyDll.lib

隐式 EXE 侧：
MyDll.h + main.c -> 编译 -> main.obj -> 链接 main.obj + MyDll.lib -> MyApp.exe

显式 EXE 侧：
main.c（不需要 MyDll.h）-> 编译 -> main.obj -> 链接 main.obj + kernel32.lib -> MyApp.exe

.h 只在编译阶段用，作用是让编译器知道 Add 长什么样（参数、返回值），以及告诉编译器“这是导入函数”。

隐式调用的 main.c：
#include “MyDll.h” // 这一行就是 .h 出现的地方
int main() { return Add(1,2); }
如果没有 .h，编译器看到 Add(1,2) 会报错：“Add 未声明”。你也可以不写 .h，直接在 main.c 里手写：
__declspec(dllimport) int Add(int a, int b);
int main() { return Add(1,2); }
效果完全一样。.h 只是把声明集中放一个文件里，方便 DLL 和 EXE 两边共用。

显式调用完全不需要 .h，因为代码里没有直接调用 Add，只有字符串 “Add”。

搞明白之前的问题，我们来研究导入表。

导入表同样属于数据目录表，所以寻找导入表和寻找导出表其实是差不多的流程。
可选PE头->NumberOfRvaAndSize、DataDirectories->数据目录表偏移->数据段的数据目录表
第一个是导出表，第二个就是我们要的导入表。

但是与导出表不同的是，对于一个exe文件而言，导出表通常只有一个，但是导入表却不同，它是可以有多个的，因为一个exe文件可以导入多个dll。引用几个dll，就会有对应的几份导入表，所以这个地方，导入表他是一个数组。

OriginalFirstThunk

也就是上来哪个联合体里的字段，它是一个RVA，它加上imagebase，就可以通过它，找到一个IMAGE_THUNK_DATA数组，这个数组就是INT——import name table。

为什么使用联合体？
因为同一个位置存储的内容，可能有不同的含义。

什么是联合体？联合体与结构体不同，联合体是联合体的成员共用一块内存空间。

为什么是一个IMAGE_THUNK_DATA数组？
因为一个DLL可能导入多个函数。

  1. 按名称导入
    如果要按名称导入，那IMAGE_THUNK_DATA存放的，就是一个RVA，这个RVA指向IMAGE_IMPORT_BY_NAME结构体。

其中NAME，是不固定大小的字符串，存放函数名称。
所以整个寻址过程就是:IMAGR_THUNK_DATA–RVA–>IMAGE_IMPORT_BY_NAME–+2(跳过Hint)–>NAME

  1. 按序号导入
    如果是按照函数序号导入

Ordinal=EAT下标+Base还记得吗？我们就按照Ordinal导入

此时IMAGE_THUNK_DATA里面存放的，就是序号信息。

而具体怎么存放呢？我们又怎么区分，这里存放的是序号信息还是指向IMAGE_IMPORT_BY_NAME的RVA呢？
因为IMAGE_THUNK_DATA使用的是联合体，他们是共用的，所以我们要区分它是那种情况，区分方法就是看最高位是1还是0。如果是1，那么就是按照序号导入的，如果是按照名称导入的，那就是按照名称导入的！

例如：

按序号导入：例如序号是0x10，那么他的IMAGE_THUNK_DATA可能就是0x80000010
前面的最高位就是1

按名称导入：例如RVA是0x400，那么他的IMAGE_THUNK_DATA可能是0x00000400
前面最高位就是0

TimeDataStamp

时间戳

ForwarderChain

转发链相关字段。

Name

他是一个RVA，指向一个字符串，里面存放的，就是DLL的名称。

FirstThunk

与OriginalFirstThunk一样，他也是存放的RVA，指向的呢，就是导入地址表IAT。
FirstThunk的RVA也指向一些IMAGE_THUNK_DATA数组，而这些数组在磁盘中时，其实与OriginalFirstThunk指向的IMAGE_THUNK_DATA数组一样，都是：如果是按名称导入，就是存放指向IMAGE_IMPORT_BY_DATA的RVA，如果是按序号导入，就存放序号信息，规则也一样。
只有到了内存中之后，加载器读取exe的导入表，找到对应的dll，查找他们的导出表，找到对应的函数的RVA，经过计算之后得到VA，也就是函数的确切地址，就将这些地址存放到IMAGE_THUNK_DATA数组的对应位置上。
